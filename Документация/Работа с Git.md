# Работа с Git
- `main`
  - tag: v1.0.0
- `develop`
- `feat/nazvanie_feature`
- `fix/isparavlenie_coda`
- `chore/infrastructura`
##  
Подробный флоу разработки сверху вниз 

👷‍♂️Инженер:
1. Делаем свою ветку из develop. пример `feat/${описание}` или  `chore/${описание}` или `fix/${описание}` 
2. При разработке в первом коммите пишем `feat ${описание}` 
   
🧠Тех лид: 
в свою очередь когда решает опубликовать релизную версию с фичами ( например набралось много веток от разрабов )
создает `release/v1.0.0` наследует с `develop`
                                            
👷‍♂️Инженер: 

для того что в PR не возникли конфликты можно сделать проверку ( если ветка develop была обновлена а вы еще на старой версии )
Синхронизация: Находясь в своей ветке , выполните `git fetch origin`. - Это обновит информацию о состоянии удаленного репозитория, не меняя ваш код.
Выполните `git rebase origin/develop`. - Git возьмет ваши новые коммиты, временно «отложит» их, обновит вашу ветку до состояния актуального develop и наложит ваши коммиты сверху. 

если на данном этапе возникли конфликты:
##
  1. Исправьте их вручную в файлах.
  2. `git add .` (пометьте исправленное).
  3. `git rebase --continue.`
  Никогда не делайте git commit во время ребейза!

  Отправка (Push): Так как rebase переписывает историю, обычный git push не сработает. Используйте: `git push origin feature-name --force-with-lease` (Использование --force-with-lease безопаснее, чем     обычный -f, так как предотвращает затирание чужой работы).
##
если не было конфликтов продолжаем:
1. делают PR и сравнивают свою ветку с `release/v1.0.0` ( ожидаем два 👍 апрува от разрабов , исправляем ошибки если нужно )
   Оформление к PR ( вылезет автоматически или же добавить,  пример: `feat #43 ${описание}`
3. делаем `squash and merge` в `release/v1.0.0` ( что б все наши коммиты с нашей ветки обьеденились в один и safe смерджились )
   
🧠Тех лид:
решает когда набралось достаточно изменений и мы готовы выгрузить релизную версию
1. Открывает PR и сравнивает релизную ветку `release/v1.0.0` ( с последними изменениями ) с main веткой 
   ( Оформление к PR  Title : `release v1.0.0 ${описание}`  , add description : `детальное описание если много изменений` )
2. ожидает два 👍 апрува и делает `squash and merge`
3. после успешного мерджа удаляем нашу релиз ветку ( так как все обновы уже в мейне )
4. идем в создание тэга , добавляем `v1.0.0` , ветка `main` ,  релиз title так же `v1.0.0` , описание можно сгенерить прям в github ui с АИ  
5. нажимает публиковать
   
Теперь у нас успешно готова релизная версия с тэгом , и главное не забыть теперь мы должны обновить нашу develop ветку так как теперь мы продолжаем разрабатывать уже с нового эталона грубо говоря

                                                  
1. Создаем новый PR :  `базовая - develop` , `сравниваем - main`   ( на всякий случай также собираем два 👍 апрува что б без ошибок ) и после так же `squash and merge` 

🎉После этого все обновилось в develop теперь новый эталон продолжаем круг по новой пока не закончатся задачи в проэкте🎉
