# Использование asyncpg для raw SQL

Краткое описание

Документ объясняет, когда и как в проекте использовать asyncpg для выполнения "чистых" SQL-запросов (raw SQL). Предназначен для разработчика, который недавно подключился к проекту; даёт практичные рекомендации, минимальные примеры и требования к тестированию.

## Кратко

asyncpg — асинхронный клиент для PostgreSQL с высокой производительностью. Его используют для случаев, где ORM (SQLAlchemy) недостаточно эффективен или выразителен: bulk-операции, сложные аналитические запросы, COPY и т.д.

## Когда использовать asyncpg

- Сложные запросы, которые тяжело или неэффективно выражаются через ORM.
- Bulk insert / COPY, операции, чувствительные к производительности.
- Низкоуровневые возможности Postgres (advisory locks, COPY, специфичные функции).

Не использовать asyncpg для обычных CRUD-операций — оставляйте это ORM (SQLAlchemy) ради читаемости и единообразия.

## Установка

Добавьте зависимость в `api/requirements.txt`:

```
asyncpg>=0.28
```

## Инициализация пула и подключение

Инициализируйте пул соединений при старте приложения и корректно закрывайте при завершении. Используйте пул, не открывайте соединение на каждый запрос.

Короткий пример (минимум кода):

```python
# инициализация однажды в startup
pool = await asyncpg.create_pool(dsn=DATABASE_URL, min_size=1, max_size=10)

# использование в репозитории
async with pool.acquire() as conn:
    rows = await conn.fetch("SELECT id, name FROM users WHERE active = $1", True)
```

Обратите внимание на параметризацию через `$1`, `$2` и т.п. — это защищает от SQL-инъекций.

## Практики безопасности и кодирования

- Всегда параметризуйте запросы. Не вставляйте значения через форматирование строк.
- Используйте пул (`create_pool`) и ограничьте размер пула согласно нагрузке.
- Оборачивайте сложные последовательности в транзакции (`async with conn.transaction():`).
- Инкапсулируйте raw SQL в слое доступа к данным (репозитории), не в контроллерах.
- Делайте ревью SQL-запросов: читаемость и оптимизация важны.

## Тестирование и CI

- Пишите интеграционные тесты с реальной тестовой БД (docker-compose). Тесты должны проверять корректность результата и, при необходимости, скорость.
- В CI обеспечьте возможность запуска таких тестов либо на отдельной job с контейнерной БД, либо маркируйте их как интеграционные и запускайте вручную.

## Документирование и ревью

- Все raw SQL-вставки должны быть задокументированы: зачем нужен raw SQL, почему ORM не подходит, оценка производительности.
