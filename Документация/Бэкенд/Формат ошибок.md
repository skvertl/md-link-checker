# Формат ошибок API

## Краткое описание
Этот документ описывает единый формат ошибок, который возвращает Backend. Он нужен, чтобы фронтенд и бэкенд одинаково понимали, что именно пошло не так, и чтобы ошибки было удобно типизировать через OpenAPI.

Документ отвечает на вопросы:
- как выглядит тело ответа при ошибке;
- какие коды ошибок использовать;
- какие HTTP-статусы возвращать в типовых сценариях (`/token`, `/session`).

---

## Принципы
1) **HTTP-статус отражает класс ошибки**
- `400` — запрос неправильный (не хватает данных, неверный формат).
- `401` — пользователь не авторизован (сессии нет, токен невалиден/просрочен).
- `500` — ошибка на стороне сервера.

2) **`message` — это машинный код ошибки**
- Это не текст для пользователя.
- Код должен быть стабильным, чтобы фронтенд мог писать обработку по нему.

3) **Один формат для всех ошибок**
- Фронтенд всегда ожидает одинаковые поля: `status`, `message`, `timestamp`.

---

## Схема ответа при ошибке
Backend возвращает JSON следующего вида:
- `status`: всегда строка `"error"`.
- `message`: код ошибки (строка из списка ниже).
- `timestamp`: время ошибки в ISO 8601 (UTC).

Пример:
```json
{
  "status": "error",
  "message": "SESSION_EXPIRED",
  "timestamp": "2025-12-20T12:43:28Z"
}
```

---

## Коды ошибок
### OAuth / токен
- `OAUTH_STATE_INVALID` — неверный `state` (защита от подмены).
- `OAUTH_CODE_INVALID` — код/токен не прошёл проверку (невалиден, просрочен, не парсится по правилам).

### Сессия
- `SESSION_MISSING` — сессии нет (токен/куки не переданы).
- `SESSION_EXPIRED` — сессия есть, но больше не действительна.

### Сервер
- `INTERNAL_ERROR` — непредвиденная ошибка сервера или внешнего сервиса.

> Примечание: если позже понадобится более детальная диагностика, можно добавлять новые `message`, не меняя формат ответа.

---

## Соответствие HTTP-статусов и ошибок
### 400 Bad Request
Когда запрос **некорректный по форме**:
- отсутствуют обязательные поля;
- неверный формат заголовков/тела запроса;
- токен не парсится как ожидается.

Обычно:
- `message: OAUTH_CODE_INVALID`
- (или `OAUTH_STATE_INVALID`, если ошибка именно в `state`)

### 401 Unauthorized
Когда запрос корректный, но **авторизация не прошла**:
- сессия отсутствует;
- токен невалиден или просрочен.

Обычно:
- `SESSION_MISSING`
- `SESSION_EXPIRED`
- `OAUTH_CODE_INVALID`

### 500 Internal Server Error
Когда проблема на стороне сервера/интеграций:
- база данных недоступна;
- исключение в коде;
- упал внешний сервис.

Обычно:
- `INTERNAL_ERROR`

## Чек-лист ответов для POST /token
### Успех
- Токен валиден → пользователь создан/обновлён → вернуть `user`
  - `200 OK`

### 400 Bad Request
- `token` отсутствует / пустой → `OAUTH_CODE_INVALID`
- `token` есть, но не парсится (неверный формат) → `OAUTH_CODE_INVALID`
- `state` не прошёл проверку (если используется) → `OAUTH_STATE_INVALID`

### 401 Unauthorized
- `token` парсится, но невалиден (подпись/срок/проверка) → `OAUTH_CODE_INVALID`

### 500 Internal Server Error
- Ошибка БД/внешнего сервиса/исключение → `INTERNAL_ERROR`

---

## Чек-лист ответов для GET /session
### Успех
- Токен валиден → сессия активна → вернуть `{ authenticated: true, user }`
  - `200 OK`

### 401 Unauthorized
- Токен/сессия не переданы → `SESSION_MISSING`
- Токен передан, но сессия истекла (если вы различаете expiry) → `SESSION_EXPIRED`
- Токен передан, но невалиден → `OAUTH_CODE_INVALID`

### 400 Bad Request
- Запрос сломан по форме (например, `Authorization` не `Bearer <token>`) → `OAUTH_CODE_INVALID`

### 500 Internal Server Error
- Ошибка БД/внешнего сервиса/исключение → `INTERNAL_ERROR`
