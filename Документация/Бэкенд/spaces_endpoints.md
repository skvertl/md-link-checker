# Spaces API — эндпойнты и логика поведения (контракт)

## Назначение документа
Этот документ фиксирует **контракт** и **критическую бизнес-логику** для функционала “Пространства (Spaces)”: какие эндпойнты существуют, что они делают, какие статусы/ошибки возвращают, и как работает **soft delete с окном 7 дней**. Контракт опирается на единый формат ошибок из `docs/Формат ошибок.md` (без 422) и текущий механизм сессий (`/session*`).

Документ нужен, чтобы:
- Frontend, Backend и QA одинаково понимали поведение API;
- исключить “у нас на фронте так, а на бэке иначе”;
- сделать поведение тестируемым (интеграционные тесты и QA API-тесты).

## Ключевые принципы

1) **Все `/spaces*` эндпойнты требуют авторизации** (проверка активной сессии).  
2) **Роль пользователя в пространстве — часть ответа** (нужна фронту для UI-ограничений).  
3) **Удаление — soft delete** (данные не пропадают сразу; есть окно восстановления).  
4) **Список пространств**:
   - возвращает **оба типа**: “мои (owner)” и “где добавлен” (роль != owner);
   - дополнительно может возвращать **удалённые менее 7 дней** (чтобы пользователь мог восстановить) — это критичный момент.
5) **Никаких OAuth2 flows** кроме уже существующего `/token`. Пространства работают поверх сессии.

---

## Термины
- **Space** — пространство (контейнер статей / проект / область знаний).
- **Membership** — связь `user ↔ space` с ролью.
- **Owner** — владелец пространства.
- **Superuser** — глобальная роль платформы (override).

---

## Авторизация и проверка сессии
Все эндпойнты `/spaces*` должны выполнять проверку “пользователь аутентифицирован” до бизнес-логики. Префикса `/api/v1` нет (как и у `/token`, `/session`).

Минимальное ожидаемое поведение:
- если нет данных сессии → `401 SESSION_MISSING`
- если сессия истекла/отозвана → `401 SESSION_EXPIRED`

> Конкретный механизм (stateful sessions в БД или signed JWT + jti) не важен для контракта `/spaces`, но важен для реализации `GET /session`.

## Роли и доступы
### Роли пространства (упрощённая модель)
Предопределённые роли (без отдельной таблицы “permissions read/write/delete” на первом этапе):
- `owner`
- `admin`
- `editor`
- `viewer`
- `superuser` (глобально)

### Наследование на статьи
На текущем этапе (по обсуждению) **достаточно ролей пространства**.  
Наследование на статьи и отдельные права статьи — будущая задача.

### Ключевые правила доступа
- **Создать пространство** может любой авторизованный пользователь → он становится `owner`.
- **Удалить пространство** может только:
  - `owner` данного пространства
  - `superuser`
- **Восстановить пространство** может:
  - `owner` — только если удалено **≤ 7 дней назад**
  - `superuser` — может восстановить **любое** (даже старше 7 дней), если бизнес-логика допускает

## Soft delete и окно 7 дней

### Зачем окно 7 дней
Окно позволяет:
- восстановить пространство при ошибочном удалении;
- показывать “удалённые недавно” для восстановления;
- сохранить данные (статьи/историю) без необратимых операций.

### Рекомендуемая модель данных (варианты)

**Вариант A (рекомендуется и ближе к текущим контрактам):**
- `deleted_at: datetime | null`
- `delete_scheduled_at: datetime | null` (обычно `deleted_at + 7 days`)

Удалено, если `deleted_at IS NOT NULL`.

**Вариант B (если нужен флаг, но потребуется следить за консистентностью):**
- `is_deleted: bool`
- `deleted_at: datetime | null`
- (опционально) `delete_scheduled_at: datetime | null`

При таком варианте обязательно обеспечить консистентность (`is_deleted=true` ⇔ `deleted_at NOT NULL`).

### Поведение списка при soft delete (критично)
**Критично:** по обсуждению в задачах/созвоне, в `GET /spaces` нужно учитывать удалённые пространства:

- обычный пользователь видит:
  - все **активные** пространства, где он состоит;
  - **удалённые пространства**, удалённые **менее 7 дней назад** (чтобы была возможность “Restore”).

- superuser (если есть админский режим/флаг) — может видеть **все** (включая удалённые), но это может быть отдельным эндпойнтом или параметром (см. ниже).

## Контракт эндпойнтов

### Общие правила ответа
- Все ответы — JSON.
- Ошибки — **единый формат** `{status, message, timestamp}`.
- В успешных ответах `message` не обязателен (обычно не нужен).

---

## GET /spaces

### Назначение
Получить список пространств, доступных текущему пользователю, включая:
- пространства, где он `owner`;
- пространства, где он добавлен (`admin/editor/viewer`);
- **удалённые менее 7 дней** (для восстановления).

### Авторизация
Требуется активная сессия.

### Ответ (200 OK)
```json
{
  "items": [
    {
      "id": "space_id",
      "name": "Space name",
      "role": "owner",
      "is_deleted": false,
      "deleted_at": null
    }
  ]
}
```

#### Поля
- `role` — роль пользователя в данном пространстве (нужна фронту)
- `is_deleted` / `deleted_at` — индикатор soft delete
  - если пространство удалено, фронт может показать “Restore” (по правилам ролей)

### Если пространств нет
- `200 OK` + `"items": []`  
Не используем `204` и тем более `404`.

### Сортировка
По обсуждению:
- сортировка может быть на фронте (пространств мало);
- если сортировать на бэке — рекомендуется:
  1) сверху owner,
  2) ниже остальные,
  3) удалённые (≤7 дней) можно показывать последними или отдельно (решение фронта).

### Ветки логики → статус → message
| Ветка логики | HTTP | message |
|---|---:|---|
| Нет сессии | 401 | SESSION_MISSING |
| Сессия истекла/отозвана | 401 | SESSION_EXPIRED |
| Успех (включая пустой список) | 200 | OK |
| Внутренняя ошибка/БД | 500 | INTERNAL_ERROR |

## POST /spaces

### Назначение
Создать новое пространство с названием из запроса.
Создатель автоматически становится `owner`.

### Авторизация
Требуется активная сессия.

### Request
```json
{
  "name": "My Space"
}
```

### Валидации
- `name` обязателен
- `name` строка
- допускаем одинаковые названия (не уникально)

### Response (201 Created)
```json
{
  "id": "new_space_id"
}
```

### Ветки логики → статус → message
| Ветка логики | HTTP | message |
|---|---:|---|
| Некорректный body (нет name / пусто / не строка) | 400 | VALIDATION_ERROR |
| Нет сессии | 401 | SESSION_MISSING |
| Сессия истекла/отозвана | 401 | SESSION_EXPIRED |
| Успех | 201 | OK |
| Внутренняя ошибка/БД | 500 | INTERNAL_ERROR |

## DELETE /spaces/{space_id}

### Назначение
Soft delete пространства (не удаляем физически).

### Авторизация
Требуется активная сессия.

### Права
- `owner` пространства или `superuser`.

### Логика
- пометить пространство как удалённое:
  - `deleted_at = now()`
  - `delete_scheduled_at = now() + 7 days` (если используем)
  - (опционально) `is_deleted = true`
- после удаления:
  - оно **не должно** считаться активным;
  - оно может появляться в `GET /spaces` как “удалённое” только в окне 7 дней (для owner).

### Response (200 OK)
```json
{
  "id": "space_id",
  "deleted": true
}
```

### Ветки логики → статус → message
| Ветка логики | HTTP | message |
|---|---:|---|
| Нет сессии | 401 | SESSION_MISSING |
| Сессия истекла/отозвана | 401 | SESSION_EXPIRED |
| Пространство не найдено | 404 | SPACE_NOT_FOUND |
| Нет прав (не owner и не superuser) | 403 | FORBIDDEN |
| Успех | 200 | OK |
| Внутренняя ошибка/БД | 500 | INTERNAL_ERROR |

---

## POST /spaces/{space_id}/restore

### Назначение
Восстановить удалённое пространство.

### Авторизация
Требуется активная сессия.

### Права
- `superuser` — может восстановить любое пространство
- `owner` — только если удаление произошло **≤ 7 дней назад**

### Логика
- сбросить soft delete поля:
  - `deleted_at = null`
  - `delete_scheduled_at = null`
  - (опционально) `is_deleted = false`

### Response (200 OK)
```json
{
  "id": "space_id",
  "restored": true
}
```

### Ветки логики → статус → message
| Ветка логики | HTTP | message |
|---|---:|---|
| Нет сессии | 401 | SESSION_MISSING |
| Сессия истекла/отозвана | 401 | SESSION_EXPIRED |
| Пространство не найдено | 404 | SPACE_NOT_FOUND |
| Нет прав (не owner и не superuser) | 403 | FORBIDDEN |
| Owner вне окна 7 дней | 403 | SPACE_RESTORE_WINDOW_EXPIRED |
| Успех | 200 | OK |
| Внутренняя ошибка/БД | 500 | INTERNAL_ERROR |

---

## Единый формат ошибок
Любая ошибка должна возвращаться в формате:
```json
{
  "status": "error",
  "message": "SESSION_EXPIRED",
  "timestamp": "2026-01-15T12:43:28Z"
}
```

### Минимальный перечень message-кодов для Spaces
- `VALIDATION_ERROR`
- `SESSION_MISSING`
- `SESSION_EXPIRED`
- `SPACE_NOT_FOUND`
- `FORBIDDEN`
- `SPACE_RESTORE_WINDOW_EXPIRED`
- `INTERNAL_ERROR`

> Новые коды (`SPACE_*`, `FORBIDDEN`) должны быть добавлены в перечисление ошибок бекенда и документированы в `docs/Формат ошибок.md` рядом с существующими (`VALIDATION_ERROR`, `SESSION_*`, `INTERNAL_ERROR`), чтобы фронт мог типизировать ответы.

## Тестовые сценарии

### GET /spaces
- без сессии → 401 SESSION_MISSING
- истекшая сессия → 401 SESSION_EXPIRED
- пользователь без пространств → 200 items=[]
- пользователь с owner+member пространствами → 200 items с role
- после soft delete:
  - удалённое пространство появляется в списке как `is_deleted=true` **если удалено ≤7 дней**
  - после 7 дней (owner) — не показывается (или показывается только superuser-режиму)

### POST /spaces
- невалидный body → 400 VALIDATION_ERROR
- успех → 201 + id
- проверка, что создатель получил роль owner (membership)

### DELETE /spaces/{id}
- не owner → 403 FORBIDDEN
- owner → 200 OK и пространство становится удалённым
- проверка: в `GET /spaces` оно помечено как удалённое (в окне 7 дней)

### RESTORE
- owner в окне 7 дней → 200 OK
- owner вне окна → 403 SPACE_RESTORE_WINDOW_EXPIRED
- superuser всегда → 200 OK

## Критические моменты и решения по умолчанию

### 1) Показывать ли удалённые пространства в GET /spaces?
**Да, но только те, что удалены ≤ 7 дней назад**, чтобы пользователь мог восстановить.  
Это обсуждено в задачах (логика “удаленные менее 7 дней возвращать”).

### 2) Как superuser “видит всё”?
Есть варианты:
- (A) отдельный эндпойнт `/admin/spaces` (лучше по архитектуре)
- (B) query param `GET /spaces?include_deleted=true` доступный только superuser

Пока можно оставить как “в будущем”, но важно зафиксировать, что **superuser может восстановить любое**.

### 3) 204 No Content vs 200 []
Выбрано: **200 + пустой список**. Это проще для фронта и тестов.

### 4) Уникальность имени
Имя пространства **не уникально**.

### 5) “Состояние пространства перед восстановлением”
Это открытый вопрос из обсуждения: нужен ли статус/процесс перед восстановлением (например “нельзя восстановить пока не переименуешь”).  
Пока в контракт не включаем — это будущая история.

### 6) Удаление “не сразу”
Физического удаления нет. “7 дней” — это окно восстановления; вопрос о hard-delete после 7 дней — отдельная задача и пока не требуется.
