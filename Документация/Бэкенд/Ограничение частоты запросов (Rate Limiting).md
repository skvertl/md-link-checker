### Бизнес-ценность

Внедрение механизма ограничения частоты запросов (Rate Limiting) позволяет защитить сервис от перегрузок и злоумышленников. Это гарантирует, что:
1. **Стабильность системы:** Один пользователь или бот не сможет замедлить работу приложения для всех остальных, создавая чрезмерную нагрузку.
2. **Защита от атак:** Снижается риск успешного проведения Brute-force атак и DDoS-атак на критические эндпоинты.
3. **Экономия ресурсов:** Оптимизируется использование серверных мощностей за счет отсечения нежелательного трафика на раннем этапе.

### Техническая реализация

Для реализации ограничений используется библиотека `slowapi`, которая интегрируется с FastAPI. Идентификация пользователя происходит по его IP-адресу.

**Пример инициализации и применения:**

```python
from fastapi import FastAPI, Request
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
from slowapi.errors import RateLimitExceeded
```

# Инициализация лимитера по IP

```python
limiter = Limiter(key_func=get_remote_address)
app = FastAPI()
app.state.limiter = limiter
```

# Регистрация обработчика ошибки превышения лимита

```python
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

@app.get("/")
@limiter.limit("10/second")
async def root(request: Request):
    return {"message": "Hello World"}
```

### Параметры декоратора

Метод `@limiter.limit()` позволяет гибко настраивать пороги доступа для каждого отдельного маршрута.

| Параметр | Тип | Описание | Обязателен |
| :--- | :--- | :--- | :--- |
| `limit_value` | `str` | Строковое описание лимита (например, "10/second", "5/minute"). | Да |
| `key_func` | `function` | Функция для определения идентификатора клиента (по умолчанию используется IP). | Нет |

### Важно

> **Внимание:** Все эндпоинты, использующие декоратор `@limiter.limit`, обязаны принимать объект `request: Request` в качестве аргумента, иначе библиотека не сможет корректно обработать входящий запрос.

> **Ошибка 429:** При превышении лимита сервер автоматически возвращает статус-код `429 Too Many Requests`. Обработка этой ошибки на стороне фронтенда должна включать информирование пользователя о необходимости подождать перед повторным запросом.
